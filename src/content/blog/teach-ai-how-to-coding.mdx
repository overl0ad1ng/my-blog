把需求交给 AI，它改文件、装依赖、跑测试，最后告诉你：完成了。

过了两周，想再加一条业务规则，打开代码却发现，一个简单功能绕了好几个文件。每一行都能看懂，连起来却不知道该从哪里改。

<Text italic bold>AI 写的代码，你还愿意接着维护吗？</Text>

2026 年 6 月 30 日，Godot 发布了贡献政策调整公告，提出收紧 AI 使用规则，包括禁止自主 AI Agent 和 vibe coding，以及用 AI 生成大段代码。文章指出，生成 PR 的成本下降了，审查它们需要的工作却没有随之减少。[Godot 政策公告](https://godotengine.org/article/contribution-policy-2026/)

维护者还提到，审查 PR 也在帮助贡献者成长，培养以后能接手项目的人。如果反馈只被交给机器，提交者始终没有理解代码，维护者花的时间就很难培养出下一位维护者。

自己的项目也一样。功能完成之后，还得有人解释代码、处理故障，继续做下一次修改。

## AI 代码一定更难维护吗？

几项研究的结论有些差别。

CodeRabbit 分析了 470 个真实开源 PR，报告中 AI 生成代码的缺陷数量约为人工代码的 1.7 倍。这个比例适用于该报告的样本，不能直接推广到所有模型和项目。[CodeRabbit 报告](https://www.coderabbit.ai/whitepapers/state-of-AI-vs-human-code-generation-report)

另一项研究比较了 2,735 个场景，发现 AI 代码的整体可读性与人工代码相当，但仍有过度复杂、冗余注释和陌生 API 用法等问题。调整提示词能有所改善，效果有限。[可读性研究，2026 年修订版](https://arxiv.org/abs/2605.13280v2)

还有一项研究，让 32 名编程初学者完成 160 次任务，成功率为 32.5%。这些初学者在理解 AI 代码、判断行为是否正确时遇到了困难。研究对象是初学者，不能据此推断有经验工程师的表现。[初学者代码理解研究](https://arxiv.org/abs/2504.19037)

在一项包含 118 名从业者的调查里，39% 认为 AI 代码更易读，34% 认为两者差不多，合计 73%。调查记录的是从业者对可读性的感受，不能据此衡量长期维护成本。[Atlassian 工业案例研究](https://arxiv.org/abs/2501.11264v3)

读懂一个函数，和知道修改它会影响什么，是两件事。可读性关注理解的成本，可维护性还包括定位问题、修改行为和验证结果的成本。

一个函数可以写得很漂亮，但它依赖的规则散在五个地方。读懂了这个函数，还是不敢动。

## 什么才是人类愿意维护的代码？

假设我们在做一个商城，要加一条优惠规则：商品小计满 200 元减 20 元，运费不参与优惠。

### Readability：可读性，让人少猜一点

看这段代码，假设金额都以分计：

```ts
const result = a >= 20000 ? a - 2000 + b : a + b;
```

算式不难。但 `a` 是商品金额，还是已经包含运费的订单总额？`b` 又是什么？光看这行代码，判断不了。

改成这样：

```ts
const discountCents = subtotalCents >= 20000 ? 2000 : 0;
const payableCents = subtotalCents - discountCents + shippingCents;
```

多了一行，却能看出优惠根据商品金额计算，运费最后加上。读者不用一边读，一边记住 `a` 和 `b` 分别代表什么。

注释也可以提供这种帮助。比如写清运费不参与优惠的业务依据，方便以后查证。至于「计算应付金额」，从代码就能看出来，可以省掉。

### Modularity：模块化，知道这次该改哪里

如果页面组件既读取商品，又判断优惠资格，还调用支付接口、发送通知，新增一条优惠规则就得检查整个结账流程。

可以让优惠模块负责计算，结账流程组织各个步骤，页面负责展示和交互。

以后从「满 200 减 20」改成「满 300 减 40」，先看优惠模块，再检查结账流程是否正确用了计算结果。

拆分时要按职责划分边界。如果修改一条规则仍要在十个文件里来回跳，文件变小了，理解起来可能更费劲。

依赖关系也要考虑。优惠计算接收商品金额就够了，没必要让它再去读取页面状态。

### Abstraction：抽象，把规则放到合适的位置

我们可以把优惠规则封装成 `calculateOrderDiscount`。调用者关心商品金额能获得多少优惠，不必到处重复判断。

但如果只有一条满减规则，就先搭一个通用规则引擎，加入注册器、策略工厂、插件系统，下一位维护者得先理解这套框架，才能找到那句减法。

抽象时也要考虑，哪些规则以后会一起变化。比如优惠资格和免运费资格，现在都判断金额是否满 200 元，但将来可能只调整免运费门槛。贸然合并，就会把两条独立的业务规则绑在一起。

决定是否抽象之前，可以先写一遍调用代码，再试着调整其中一条规则。调用起来是否容易理解、修改会影响哪里，比少写了几行更有参考价值。

### Consistency：一致性，沿用项目的约定

假如项目统一用分表示金额，新功能却用元；其他模块叫商品小计，新模块却把同一个数叫订单总额，接手的人就容易算错或误解。

同一个名称应该有相同的含义。处理同类问题，可以先参考已有实现，少引入一套需要重新理解的约定。

现有方式确实有问题时，可以改，但要说明原因和影响范围。否则每次生成都换一套做法，维护者就得逐个确认：这里的金额用什么单位，那里又按什么规则算。

### Testability：可测试性，改完能确认结果

满 200 减 20，那么 199.99 元、200 元、200.01 元分别怎么算？商品 180 元，加上 30 元运费，能不能获得优惠？

把这些边界的预期结果写进测试，以后改规则时就能检查有没有算错。

优惠计算直接接收金额、返回结果，就容易验证。如果必须打开页面、登录账号、连接支付服务才能检查一条满减规则，可以考虑把计算单独拆出来。

## 为什么 AI 容易写出难维护的代码？

AI 能写出好维护的代码，但任务要求和提供的上下文会影响结果。

「加一个满减功能」只交代了功能，没有说规则放在哪里、沿用什么接口、哪些行为不能改变。AI 可能交出一个能演示的方案，而我们对维护的要求从头到尾都没提过。

上下文不完整时，也容易重复实现。只给它一个页面文件，它可能在页面里完成所有工作。项目已有的金额类型、优惠模块和错误处理方式，如果没有被找到，就可能再写一遍。

连续修补也会增加复杂度。报错了，加一个判断；结果不对，再加一个特殊分支。每次都解决眼前的问题，却没人检查这些分支是否该放在一起。人类也会这样写，AI 生成得快，我们更容易来不及回头看。

等到功能跑起来，又直接进入下一个任务。重复规则、模糊命名和绕远的依赖留在代码里，下次生成时还可能被当成参考。

这些问题需要在提出需求和检查结果时处理。只以「能跑」验收，很容易漏掉它们。

## 怎样教 AI 写出可维护的代码

这里的「教」，就是把维护要求告诉 AI，让它在写代码和检查代码时照着做。规则可以保存在项目里，供后续任务读取，但一次对话不会让模型永久学会这些原则。

### Prompt：把「好代码」说具体

「请遵循最佳实践，保证可维护性」没有说清要检查什么。订单需求可以具体写成这样：

```text
为订单增加「商品小计满 200 元减 20 元」的规则，运费不参与。

先阅读现有结账流程、金额表示和优惠模块，说明规则应该放在哪里。
沿用项目已有的金额单位、命名和接口。
让优惠计算可以独立验证，不依赖页面状态或支付服务。
只实现当前规则；新增抽象时，说明它解决了什么实际问题。
验证门槛以下、恰好达到门槛，以及运费不参与优惠的情况。
完成后说明修改范围、验证结果和仍未确认的假设。
```

边界明确的小修改，可以直接实现。牵涉多个模块时，先让 AI 解释数据从哪里来、规则由谁负责。如果它准备在页面里计算优惠，我们在动手之前就能指出问题。

### AGENTS.md：让项目原则留在项目里

每次都在 Prompt 里重复金额单位、模块职责和检查要求，容易漏写。

可以把这些约定写进 AGENTS.md，向编程 Agent 说明项目结构和工作要求。是否自动读取、如何生效，要确认所用工具的支持方式。[AGENTS.md 官方说明](https://agents.md/)

对于刚才的商城，可以写：

```md
# 项目原则

- 修改前阅读相关模块和同类实现，确认数据来源与职责边界。
- 金额统一以整数分表示；商品小计与运费使用不同名称。
- 优惠规则由优惠模块维护，页面和支付适配层不重复实现。
- 优惠计算显式接收输入，不读取页面状态或直接发起网络请求。
- 新增抽象必须有当前需求依据，不为假想扩展搭建框架。
- 修改规则后验证关键边界，报告实际执行的检查及其结果。
```

实际项目还可以补充目录说明、已有接口，以及准确的检查命令。

优先写新加入的人容易误解的约定，比如金额单位和规则归属，不必堆几十条通用口号。项目结构改了，相关说明也要更新，免得 AI 按过期指导继续写。

### Skills：让原则成为工作流程

「修改前先理解架构」还可以写得更具体：读哪些模块，追踪哪些调用，动手之前要确认什么。

这些步骤可以写成 Skill。按 Agent Skills 规范，一个 Skill 至少包含 `SKILL.md`，写明名称、适用场景和指令，也可以附带参考资料或脚本。[Agent Skills 规范](https://agentskills.io/specification)

比如，在工具支持的技能目录中建立 `order-rule-change/SKILL.md`：

```md
---
name: order-rule-change
description: 新增或修改订单优惠规则时使用，检查职责边界并验证金额行为。
---

1. 读取适用的项目原则，追踪商品小计、优惠和运费的计算路径。
2. 确认规则归属，说明修改位置、影响范围和需要澄清的业务条件。
3. 沿用现有金额单位与接口，实现满足当前需求的最小改动。
4. 验证优惠门槛、运费排除和原有规则，记录实际结果。
5. 检查 diff 中的重复规则、隐式依赖和多余抽象，修正后重新验证。
```

技能目录和调用方式取决于工具。写完之后，可以让 AI 用它处理一次订单修改，检查它有没有读取相关模块、验证边界，并报告实际结果。

后续任务用 Prompt 交代需求，AGENTS.md 提供长期约定，再按需要调用 Skill 执行步骤，不用每次重新写一份完整流程。

### Code Review：让 AI 回头检查自己的决定

实现完成后，可以让 AI 按维护者接手代码的要求审查：

```text
请审查本次实际 diff，并结合相关调用方、项目原则和测试判断：
- 优惠规则是否放在正确模块，是否在其他地方重复实现？
- 商品小计、运费和金额单位是否清楚且一致？
- 是否引入隐式状态、无必要的抽象或不相关修改？
- 下次调整优惠门槛时，需要修改哪些位置？
- 测试是否覆盖优惠门槛和运费排除等业务预期？

每项问题给出文件位置、影响和代码依据；没有证据的疑虑标为待确认。
先报告发现，再修正有依据的问题，并重新运行受影响的检查。
明确区分已验证结果与尚未验证的判断。
```

审查要结合调用方和业务要求。比如页面又算了一遍优惠，或者测试照抄了实现里的公式，却没覆盖运费排除，都需要检查。

自审可能沿用实现时的错误假设，所以还要核对它给出的依据。AI 报告「没有发现问题」，也不能保证代码没有问题。

优惠门槛是否正确、运费是否参与，都要由人确认。AI 可以帮忙追踪代码、执行检查，提交修改的人仍需要理解设计并负责后续维护。

## Writing code for humans

代码的下一位读者，可能是同事，也可能是两周后的自己。到那时，聊天记录里的解释未必还在眼前，需求却已经变了。

接手的人得弄清楚，为什么运费不参与优惠，为什么这条规则放在这里，以及改动之后会影响什么。我们今天花时间讲清楚的这些事，应该也能在代码里找到依据。

代码往往会比生成它的那次对话留得更久。写给人看的代码，是把当时的理解留给后来的人，让他们能够继续做自己的判断。

<Text italic bold>当生成代码变得越来越容易，我们还会花多少心思，让另一个人读懂它？</Text>
